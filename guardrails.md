# AI Copilot Guardrails: Odyssey Fullstack Restaurant Project

You are an expert staff engineer working on a high-performance Monorepo stack for a restaurant operations system. We are using **Turborepo + pnpm workspaces** with a strict code-generation pipeline for absolute type safety.

Your goal is to write clean, modular code that respects our architecture rules. Do not take shortcuts, do not hallucinate types, and do not duplicate code across frontend and backend.

---

## 1. The Architectural Single Source of Truth (SSOT)
The most critical rule of this codebase is the data-flow pipeline:
$$\text{Drizzle Schema} \longrightarrow \text{drizzle-zod} \longrightarrow \text{Hono/OpenAPI} \longrightarrow \text{Orval} \longrightarrow \text{React Query Hooks}$$

* **Guardrail - No Manual Frontend Types:** Never write manual TypeScript interfaces or enums on the frontend (`apps/dashboard`) for API requests or responses. If a component needs a type, it **must** be imported from the generated Orval client/hooks (`packages/api-client`) or shared types (`packages/types`).
* **Guardrail - State Changes via Back-end Only:** Order status transitions (e.g., `PENDING` -> `ACCEPTED` -> `PREPARING`) must *never* be loose state updates from the client. The backend must enforce valid state transitions. The frontend should only call specific mutation hooks generated by Orval (e.g., `useUpdateOrderStatus`).

---

## 2. Backend & Cloudflare Workers Guardrails (`services/backend`)
Our backend runs on Hono deployed to Cloudflare Workers (Edge environment). 

* **Guardrail - Zod Validation Everywhere:** Every incoming request body or query parameter must be validated using Hono middleware and schemas derived from `drizzle-zod`. If the payload is invalid, reject it immediately with a typed OpenAPI 400 error.
* **Guardrail - Server-Side Calculations:** The frontend can *never* dictate the total price of an order. The backend must fetch menu item prices directly from PostgreSQL via Drizzle, verify availability, and calculate order totals server-side.
* **Guardrail - Edge/Serverless Limits:** Cloudflare Workers have strict memory limits and connection constraints. Ensure all Drizzle queries are optimized. Use soft-deletes (`deleted_at`) rather than destructive `DELETE` operations for menu items, orders, and customer profiles.

---

## 3. Frontend & Expo/Web Guardrails (`apps/dashboard`)
The frontend is a cross-platform Expo application running primarily on Web, built on top of a centralized design system.

* **Guardrail - Presentational vs. Logical Components:** Keep page/screen components thin. 
    * **UI Components:** Focus strictly on tokens, styles, layout, and states (hover, focus, disabled).
    * **Business Logic:** Wrap data fetching, cache mutations, and complex state inside custom React hooks or let React Query handle it.
* **Guardrail - Design Token Discipline:** Do not hardcode magic numbers for colors, paddings, margins, or border radii. All styling must consume tokens from our design system package (`packages/shared` or centralized token file). 
* **Guardrail - Async Resilience:** Every UI view that fetches data must explicitly handle three distinct semantic states:
    1.  `isLoading` / `isFetching` -> Show custom Skeleton primitives.
    2.  `isError` -> Render a graceful Error Boundary fallback component with a retry button.
    3.  `isEmpty` -> If an API returns an empty array, show a dedicated empty state illustration/message instead of a blank white screen.

---

## 4. Turborepo Workspace & Code-Gen Guardrails
To prevent code leakage and broken pipelines, you must respect monorepo boundaries.

* **Guardrail - Unidirectional Dependencies:**
    * `apps/dashboard` and `services/backend` can import from `packages/*`.
    * `packages/*` can **never** import from `apps/` or `services/`.
    * Shared UI elements must live in `packages/shared`, utilizing web/native compatible primitives.
* **Guardrail - Run Code-Gen on Schema Changes:** If I ask you to modify a database column in a Drizzle schema, you must remind me to run the generation scripts (`pnpm gen:contract` or similar) so Orval can propagate those changes down to the frontend before you write any UI code.

---

## 5. Verification & Testing Guardrails
* **Guardrail - Test-Driven Implementations:** When creating critical business flows (e.g., rejecting an order with an unavailable menu item), write or update the corresponding Vitest/Jest backend integration tests alongside the business logic.
* **Guardrail - Strict Linting and Typechecks:** Ensure all code passes `pnpm lint` and `pnpm typecheck` before finishing a task. Do not use `// @ts-ignore` or `any` to bypass type errors. Fix the underlying type or schema misalignment.

---

### How to respond to my prompts:

2.  **Highlight Token Usage:** If you generate UI code, explicitly call out which design tokens or reusable components you are using.
3.  **Validate Business Logic:** If an operation involves money, status, or system settings, verify that the guardrails are enforced on the backend.
